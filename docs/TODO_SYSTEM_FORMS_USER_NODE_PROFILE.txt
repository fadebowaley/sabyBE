# TODO: System Forms (User Profile + Node Profile)

Date: 2026-04-08
Owner: Backend + Form Studio
Status: Phase A-C complete, Phase D in progress

## 1) Goal

Introduce a new `system` form category in ProjectForm so every tenant always has two standard secure forms:

1. `User Profile` system form
2. `Node Profile` system form

These forms should behave like standard forms (short code, share reference, form renderer UX), but submission writes directly to system records (`User` / `Nodes`) instead of generic data submission storage.

## 2) Current Architecture Findings

### 2.1 Existing schema sources of truth

- User profile is embedded in `User` model:
  - `src/models/user.model.js`
- Node profile is embedded in `Nodes` model:
  - `src/models/node.model.js`

There are no separate `UserProfile` or `NodeProfile` collections.

### 2.2 Existing update APIs already available

- User update endpoint:
  - `PATCH /v1/users/:userId`
  - route: `src/routes/v1/user.route.js`
  - validation: `src/validations/user.validation.js`
  - service mapping: `src/services/user.service.js` (`updateUserById`)
- Node update endpoint:
  - `PATCH /v1/node/:nodeId`
  - route: `src/routes/v1/node.route.js`
  - validation: `src/validations/node.validation.js`
  - service mapping: `src/services/node.service.js` (`updateNodeById`)

### 2.3 Existing standard form infrastructure

- Standard form model with share/public references is already present:
  - `publicRef`, `shareRef`, `shareCode`, `formReference`
  - `src/models/projectForm.model.js`
- Public form and secure access routes already exist:
  - `src/routes/v1/projectForm.route.js`
- Secure public mode exists (`single_qr_passwordless`) and can be reused for protected system forms.

## 4) Required Form Metadata Contract (new)

Add metadata for system forms:

- `metadata.formCategory = "system"`
- `metadata.systemTarget = "user_profile" | "node_profile"`
- `metadata.systemVersion = "1.0.0"`
- `configuration.security = "private"` (enforced)
- `configuration.publicSecureMode = "off"` for dashboard-only mode by default

Optional future setting:

- `metadata.systemSubmissionMode = "direct_update"`

## 5) Submission Strategy (key difference)

Standard forms currently submit into submission pipeline.
System forms should instead:

1. resolve authenticated actor + tenant context
2. validate that actor can update target record
3. map form payload to existing update DTO
4. call existing update services
   - `userService.updateUserById(...)`
   - `nodeService.updateNodeById(...)`
5. return updated entity payload
6. emit audit log (`system_form_submission`)

No new profile collections should be created.

## 6) Security + Access Rules

System forms are authenticated-only.

- User Profile form:
  - user can edit own profile
  - elevated roles can edit other users if existing permission allows
- Node Profile form:
  - must respect `node:update` permission and tenant ownership check

All submissions must enforce:

- tenant match
- permission check
- field allowlist based on validation schemas

## 7) Tenant Bootstrap Requirements

On tenant creation (or on first access if missing), auto-provision:

1. `User Profile` system form
2. `Node Profile` system form

Each provisioned form should have:

- generated `projectId`
- generated `publicRef/shareRef/shareCode`
- deterministic `metadata.systemTarget`
- locked core element bindings (`metadata.bindingPath`) for DB-safe mapping

## 8) Form Studio/Renderer Behavior Requirements

System forms should look and behave like normal forms, but:

- mark bound fields as `system-bound`
- restrict unsafe edits:
  - disallow changing critical binding path IDs
  - allow label/help/placeholder changes
- keep references and links visible like standard forms

Renderer should still use current form engine; only submission handler changes based on `metadata.formCategory`.

## 9) API Changes Needed (planned)

1. Add system form submit endpoint (authenticated):
   - `POST /v1/project-forms/system/:publicRef/submit`
2. Add bootstrap endpoint (admin/internal):
   - `POST /v1/project-forms/system/bootstrap`
3. Add retrieval filter:
   - `?formCategory=system`

Compatibility:

- existing project-form APIs remain unchanged
- generic submissions pipeline remains unchanged for non-system forms

## 14) API Center Visibility and Differentiation

Both system forms must appear in API Center because they are standard `ProjectForm` records with reference IDs and short links.

Required UI distinction in API Center list:

- `Category` badge: `System`
- `Target` badge: `User Profile` or `Node Profile`
- `Submission` badge: `Direct DB Update`
- `Security` badge: `Auth Required`
- Optional icon: shield/gear for system forms

Behavior differences from normal forms:

- No anonymous public submission for system forms
- Opens authenticated secure flow only
- Uses direct update endpoints (User/Node services), not generic form submission storage

---

## Recommendation to start

Start with `User Profile` only (Phase A-C), then `Node Profile` after submit-path is stable. This reduces blast radius and validates the direct-update form pattern before adding node-specific authorization complexity.
